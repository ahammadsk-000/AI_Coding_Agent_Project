AI Coding Agent — agentic RAG platform over your codebase

Overview

A self-hostable agentic RAG platform over your codebase: point it at a GitHub repo, it clones and indexes the code with tree-sitter + embeddings, and then you can search it (hybrid retrieval), chat with a RAG + tool-using agent, run a multi-agent pipeline, audit the code, and open PRs.

One sentence drives the design: "an indexing + retrieval + agentic-orchestration system where the quality of retrieval determines the quality of every answer." That makes it a data-pipeline + RAG + agent-loop problem, not a CRUD app.

Module 1 — Repository Ingestion

Ingestion is the offline indexing pipeline that turns a git repo into a searchable hybrid index. Nothing else works until it runs — search, chat, agents, insights all read what it produces. It's the "Phase 1 of RAG": indexing, done once, ahead of time.

STEP 1Why this module exists
  • RAG has two halves — offline indexing and online retrieval. This is the indexing half; without it there's nothing to retrieve.
  • Search, chat, agents, insights, and audit are all consumers of the index it builds. It's upstream of everything.
  • The quality of chunking here caps the quality of every answer downstream — a chunk split mid-function retrieves and grounds poorly.
One-liner: "Ingestion is the offline pipeline that turns a repo into a searchable hybrid index. It's upstream of every feature, and its chunking quality caps retrieval quality — so it's where the real leverage is."
STEP 2Where it fits

It's the entry point of the data flow and runs as a background job, not on the web request (cloning + parsing + embedding is slow + CPU-heavy). Two execution modes, one pipeline:

  • Celery task (tasks/ingest.py) — normal, scalable.
  • Inline subprocess (app/ingest_cli.py) — free-tier deploy with no worker; its own async engine + event loop so it never reuses the API's pool.
Key decision: keep heavy work off the request thread. The API just creates a job row and dispatches; the client polls or streams progress.
STEP 3How it communicates

It's decoupled — it doesn't call other domains synchronously. It:

  • Writes to Postgres (files/symbols/chunks) and Qdrant (vectors).
  • Publishes progress to a Redis pub/sub channel keyed by job id.
  • The API's SSE endpoint subscribes to that channel and forwards events to the browser.
# worker publishes; the API's /jobs/{id}/events SSE endpoint subscribes
await redis.publish(f"ingest:events:{job_id}", json.dumps(progress))
Why pub/sub + SSE: the worker and the web process are different processes — Redis is the message bus between them; SSE is one-way progress to the UI.

STEP 6Pipeline flow — clone → parse → chunk → embed → index
  1. Trigger: create IngestJob (queued), flip repo → ingesting, commit, dispatch.
  2. Clone: shallow git clone --depth=1 (URL-validated, size-capped, .git removed).
  3. Walk & filter: skip ignored dirs / oversized / binary; detect language per file.
  4. Parse: tree-sitter → extract symbols (functions/classes) with line spans.
  5. Chunk: AST-aware on symbol boundaries, tiktoken-budgeted; oversized symbols → line-window; unsupported langs → plain line-window.
  6. Embed: batch chunks → embedding provider → one vector each.
  7. Index: upsert vectors to Qdrant + write files/symbols/chunks to Postgres.
  8. Publish + finish: stream progress to Redis → SSE; mark job succeeded, repo ready.
clone ──▶ walk/detect ──▶ tree-sitter ──▶ AST chunk ──▶ embed(batch) ──▶ Qdrant + Postgres ──▶ ready └─ progress ──▶ Redis ──▶ SSE ──▶ UI
STEP 7Edge cases
  • Huge repo — bounded clone (depth 1 + size cap) truncates rather than OOM.
  • Unsupported language — no tree-sitter grammar → fall back to line-window chunking (still searchable).
  • tree-sitter yields no symbols (a prod quirk) — chunking still works via line-window; the code-map feature falls back to the file tree.
  • Embedding 429 / rate limit — retry with exponential backoff; batch so one failure doesn't sink the run.
  • Re-ingest — currently a full re-index (replaces the repo's data).
  • No worker (free tier) — inline subprocess path runs the identical pipeline.
STEP 8Best practices
  • AST-aware chunking — chunks are whole functions, not arbitrary slices.
  • Background job — never block the web request on clone/parse/embed.
  • Batch embeddings (≤256) — throughput + rate-limit friendliness.
  • Token-budgeted chunks (tiktoken) — predictable embedding + prompt sizes.
  • Stream progress — the user sees files/chunks tick up live (SSE).
  • Two stores, each best-fit — vectors in Qdrant, text + FTS in Postgres.
STEP 9Security concerns
  • SSRF / malicious URLs — validate the git URL before cloning.
  • DoS via huge repos — hard size + depth caps.
  • No code execution — ingestion only reads/parses files; it never runs repo code (that's the sandbox's job, isolated).
  • Isolation — .git removed post-clone; work in a scoped temp dir.
  • Ownership — a user can only ingest repos they own (authz in the service).
STEP 10Scalability
  • Workers scale independently — add Celery workers to parallelize ingestion across repos.
  • Batched embeddings — the main cost; batching + backoff keeps within provider limits.
  • Per-repo Qdrant collections — smaller HNSW graphs = faster search; drop/rebuild per repo.
  • Bottlenecks: embedding rate limits + ingestion memory on giant repos.
Gold: "How would you make re-ingest cheap?" → Incremental indexing — diff against the last indexed commit SHA and only re-process changed files.
STEP 11How industry does it

Large code-search systems (GitHub code search / Zoekt, Sourcegraph) run the same shape at scale: parse + index, incremental indexing on every commit, distributed indexers, and trigram/semantic hybrid indexes. Modern "chat with your code" tools (Cursor, Cody) add the embedding + retrieval layer on top — exactly this pipeline. The scaling path from here is incremental ingestion + a distributed indexer pool.

💬 Interview Q&A

Why AST-aware chunking instead of fixed-size? A chunk should be a semantically whole unit (a function/class). Fixed-size splits functions mid-body, which embeds poorly and breaks grounding. tree-sitter gives real symbol boundaries.
Why run ingestion as a background job? Clone + parse + embed is slow and CPU-heavy; doing it on the request would block the API and time out. A job row + Celery/subprocess keeps the API responsive; progress streams via SSE.
Why one Qdrant collection per repo, not one shared collection? Isolation (drop/re-ingest = delete a collection), smaller per-repo HNSW graphs (faster), and no cross-repo leakage. Trade-off: cross-repo search must query several collections and merge.
What if tree-sitter doesn't support a language? Fall back to line-window chunking — the file is still indexed and searchable, just without symbol-aware boundaries.
How do you handle a giant repo or a rate-limited embedder? Bounded clone (depth 1 + size cap); batch embeddings with retry + exponential backoff so a 429 doesn't fail the whole run.
Why store chunk text in Postgres but vectors in Qdrant? Keep the vector store lean — Qdrant holds the vector + a tiny payload (ids, lines); search hydrates the full content from Postgres by id. Separation of concerns.

⚠️ Common mistakes this module avoids

  • Fixed-size / character chunking that splits functions mid-body.
  • Running clone/embed synchronously on the web request (blocks + times out).
  • Embedding one chunk at a time (slow, rate-limit-prone) instead of batching.
  • No progress feedback (users stare at a spinner) — solved with pub/sub → SSE.
  • Dumping full chunk text into the vector DB payload (bloats it) instead of hydrating from Postgres.

Module 2 — Hybrid Search & RAG

The retrieval core — the online half of RAG. Given a question, it finds the most relevant code chunks by running dense (semantic) and sparse (keyword) search in parallel, fusing them, and reranking. Because a great LLM can't fix bad retrieval, this module's quality caps every answer's quality in the whole app.

Files in this module

api/v1/search.py                  POST /search · POST /context/build
domain/search/
├── service.py                    SearchService — the hybrid pipeline (dense ∥ sparse → RRF → rerank)
├── context.py                    pack_context() — token-budgeted context assembly
└── schemas.py                    SearchHit (carries dense/lexical/rerank sub-scores)
infrastructure/qdrant/client.py   dense kNN (HNSW, cosine, per-repo collection)
infrastructure/embeddings/reranker.py   cross-encoder (ms-marco-MiniLM), lazy-loaded
STEP 1Why this module exists
  • RAG's online half. Ingestion built the index; this uses it — turning a question into the handful of chunks the LLM will reason over.
  • Retrieval quality is the whole game. If the right code isn't retrieved, no model can answer well. This is the highest-leverage module.
  • Every AI feature depends on it — chat, agents, eval, and the similar-code finder all call SearchService.search().
One-liner: "Hybrid search decides which code the LLM gets to see. A great model can't fix bad retrieval — so this is where I spend the effort: dense + sparse + fusion + rerank."
STEP 2Where it fits

It sits between ingestion and generation: ingestion produces the index, this retrieves from it, and chat/agents feed the result to the LLM. It's a shared service, not an endpoint — called directly by /search, and internally by chat (RAG context), each agent researcher, the eval harness, and insights.

Design point: retrieval is centralized in one SearchService so every feature gets the same tuned pipeline — fix RRF or rerank once, everything improves.
STEP 3How it communicates

It reads two stores in parallel and returns plain result objects:

# dense and sparse run concurrently, then fuse
dense, lexical = await asyncio.gather(
    self._dense_search(repo_ids, query=query, limit=pool),   # Qdrant kNN
    self._lexical_search(repo_ids, query=query, limit=pool), # Postgres FTS
)
candidates = _rrf_fuse([dense, lexical])                      # rank-based fusion

Output is a list of SearchHit (path, lines, content, sub-scores). pack_context() then turns hits into a token-budgeted prompt block for the LLM.

STEP 4Data & stores

No new tables — it reads what ingestion wrote:

StoreUsed for

code_chunks.content_tsv (GIN index)sparse full-text (ts_rank_cd)

Interview detail: a dense hit from Qdrant carries only ids + lines; the service hydrates the full content from Postgres by chunk id — the two stores are joined at query time, not duplicated.
STEP 5APIs
EndpointPurpose
POST /api/v1/searchranked hits — params: query, repository_ids, k, mode (hybrid/dense/lexical), rerank

STEP 6Retrieval flow
  1. Authorize — resolve which of the caller's ready repos to search.
  2. Embed the query → a vector.
  3. Dense ∥ Sparse — Qdrant kNN and Postgres ts_rank_cd run concurrently, each returning a bigger-than-k pool.
  4. RRF fuse — Σ 1/(k+rank), k=60 — combine on rank, not raw score.
  5. Rerank (optional) — cross-encoder re-scores the top-N pool for precision.
  6. Filter padding — drop low-relevance dense-only hits on small corpora.
  7. Top-k + hydrate → SearchHits. (Then pack_context for RAG.)
query ─▶ embed ─┬─▶ Qdrant kNN (dense) ─┐ └─▶ Postgres FTS (sparse) ─┴─▶ RRF fuse ─▶ rerank(top-N) ─▶ filter ─▶ top-k ─▶ pack_context ─▶ LLM
STEP 7Edge cases
  • Small corpus "padding" — dense kNN always returns something; _filter_padding drops dense-only hits below a cosine floor (~0.55) unless they also matched lexically.
  • No ready repos — return empty fast (an unfinished ingest has no collection to query).
  • Reranker fails to load — best-effort: silently fall back to the fused order.
  • Weird query text — plainto_tsquery is forgiving (no FTS syntax errors on raw input).
  • Orphan Qdrant points (chunk deleted in Postgres) — hydration leaves path=""; those are filtered out.
STEP 8Best practices
  • Run dense + sparse in parallel (asyncio.gather) — latency = the slower of the two, not the sum.
  • Fuse on rank (RRF) — no fragile score normalization across incomparable scales.
  • Rerank only the top-N — the cross-encoder is expensive; never run it on the corpus.
  • Token-budget the context — merge overlapping ranges, pack under ~1500 tokens.
  • Return sub-scores — SearchHit carries dense/lexical/rerank scores for transparency + debugging.
STEP 9Security concerns
  • Tenant isolation — _authorize_repos filters to the caller's own ready repos; you can never search someone else's code.
  • No FTS injection — plainto_tsquery treats input as plain tokens, not a query language.
  • Parameterized SQL — bound params (expanding IN lists), never string-built queries.
STEP 10Scalability
  • ANN, not exact — HNSW is ~log-time; exact kNN would be a linear scan.
  • Rerank is the cost — CPU-bound cross-encoder, top-N only; it's the main latency lever (toggle off for speed).
  • Per-repo collections — smaller HNSW graphs → faster search.
  • Caching opportunity — query embeddings are deterministic; caching them (and results) in Redis is the biggest untapped win.
Gold: "Biggest latency lever?" → the cross-encoder rerank. It's a toggle applied to a small pool, so you trade a little precision for a lot of speed on hot paths.
STEP 11How industry does it

Hybrid + rerank is the production-RAG standard. Elastic and Vespa ship built-in hybrid (BM25 + vectors); Cohere/Voyage sell rerank APIs; ColBERT pioneered late-interaction retrieval. The advanced path from here — the stuff senior RAG engineers add — is query rewriting / multi-query, HyDE (hypothetical-document embeddings), and parent-child (small-to-big) retrieval, plus a labeled eval set to prove each change helps. The through-line everywhere: retrieval quality is the whole game.

💬 Interview Q&A

Why hybrid search instead of pure vector similarity? Dense captures meaning ("how are users logged in" → authenticate()); sparse/BM25 captures exact tokens (the identifier RefreshToken). Code is searched both ways, so pure vectors miss exact matches. Run both in parallel and fuse.
What is RRF, and why fuse on rank instead of adding the scores? Reciprocal Rank Fusion: Σ 1/(k+rank), k=60. Cosine (0–1) and ts_rank_cd (unbounded) are on incomparable scales — adding them lets the bigger-scale score dominate. Rank normalizes that: "rank #1" means best-in-list regardless of the raw number.
Bi-encoder vs cross-encoder — where does each go? Bi-encoder embeds query and doc separately (cacheable, fast) → used for retrieval. Cross-encoder encodes the pair together (accurate, uncacheable) → used for reranking a small top-N. Different jobs.
A small repo returns irrelevant chunks — why, and how do you fix it? Dense kNN always returns k results even if similarity is low ("padding"). Fix: after fusion, drop dense-only hits below a cosine floor unless they also matched lexically (the _filter_padding step).
How do you fit retrieved code into the context window? pack_context groups hits by file, merges overlapping/adjacent line ranges, and greedily packs under a ~1500-token budget (tiktoken). The context window is a budget you architect, not a dump.
When would dense beat sparse, and vice versa? Dense wins on paraphrase / concept queries ("auth flow"); sparse wins on exact identifiers, error strings, rare tokens. Hybrid gets both — which is the point.

⚠️ Common mistakes this module avoids

  • Pure vector search that misses exact identifiers / function names.
  • Averaging incomparable dense + sparse scores instead of rank-fusing.
  • Reranking the whole corpus (should be a small top-N pool).
  • Dumping every hit into the prompt instead of token-budgeting the context.
  • Running dense then sparse sequentially instead of in parallel.

Module 3 — Chat Agent (ReAct loop)

The conversational front door: a single tool-using agent that answers questions about your code. It grounds in RAG context, can call read-only tools, streams tokens over WebSocket, remembers durable facts, and self-guards against runaway loops.

Files in this module

├── models.py                     Conversation, Message (role, content, tool_calls, citations)
├── repository.py                 ConversationRepo, MessageRepo
├── schemas.py                    WsToken / WsToolCall* / WsCitations / WsDone / WsError

STEP 1Why this module exists
  • It's the interactive interface — natural-language Q&A grounded in the user's code, with citations.
  • It's the project's "agent" in the truest sense: the LLM decides whether to call a tool and when it's done.
  • It ties everything together — RAG (Module 2) + tools + streaming + memory in one loop.
One-liner: "The chat is a ReAct tool-using agent grounded in hybrid retrieval — it reasons, calls read-only tools, and streams a cited answer, with guardrails so a model can't run away."
STEP 2Where it fits

It's a consumer of Module 2 (calls SearchService for RAG context and via the search_code tool), the LLM provider abstraction (Module 10), and memory (Module 6). The transport (api/v1/chat.py) is thin; all logic lives in ChatService.

STEP 3How it communicates

WebSocket (bidirectional — send a message, stream tokens back, allow "stop"). The service is a Python async generator yielding typed events the WS layer serializes:

async for event in service.send_message_streaming(user, conv_id, text):
    await ws.send_json(event.model_dump(mode="json"))   # WsToken / WsToolCallStart / WsCitations / WsDone
Detail: WS auth is via ?access_token= — browsers can't set an Authorization header on the WebSocket handshake.
STEP 4Data & stores
TableRole
conversationsowner, title, scoped repository_ids, provider/model
messagesrole (user/assistant/tool), content, tool_calls, citations, token_count

Every message — including tool results — is persisted, so a conversation is fully replayable.

STEP 5APIs

REST CRUD under /api/v1/conversations/ (create/list/get/rename/delete) + a WebSocket /{id}/ws for streaming a reply.

STEP 6The agent loop (ReAct)
  1. Persist the user message; detect chit-chat (skip RAG) or a "remember X" cue (auto-save a memory).
  2. Build the prompt: system prompt + RAG context (~1500 tok) + repo inventory + recalled memories + tool defs.
  3. Stream the LLM. Text deltas → the user; tool_calls → collected.
  4. If tool calls: de-dup + cap (2/round, 3/turn), execute, append results, loop (≤5 rounds).
  5. No tool calls → that text is the final answer. Persist everything; emit citations.
prompt(RAG + tools) ─▶ stream LLM ─┬─ text ─▶ user └─ tool_calls ─▶ execute ─▶ feed back ─▶ (loop ≤5) ─▶ no tool call = done
STEP 7Edge cases
  • Chit-chat ("hi", "thanks") — skip the expensive RAG search + don't offer tools.
  • Leaked tool call (a small model writes the call as text) — detected and replaced with a clear message.
  • tool_use_failed (Groq can't parse the call) — retry the round without tools so it answers in prose.
  • Rate-limit / 413 — terminal with a friendly message (don't retry the same oversized request).
  • Runaway tool spam — de-dup + caps (the real bug that motivated the guardrails).
STEP 8Best practices
  • Thin router / fat service — the WS endpoint just pumps events.
  • Stream everything — token-by-token + tool-call + citation events.
  • Ground + cite — force file:line citations; preload the repo inventory so paths are real.
  • Guardrails — de-dup/cap tool calls, cap result size, handle rate limits gracefully.
  • Persist every message (incl. tool) — replayable, auditable.
STEP 9Security concerns
  • Read-only tools — the agent can't mutate state; writes go through gated flows (PR / sandbox).
  • Prompt injection — treat retrieved content as untrusted; never execute model output; detect leaked calls.
  • Ownership — tools search only the caller's repos; WS auth via signed token.
STEP 10Scalability
  • Stateless service — scales horizontally; conversation state is in Postgres.
  • Token caps (tool caps + context budget) keep each request under the free-tier TPM ceiling.
  • The LLM dominates latency — streaming makes time-to-first-token the felt latency.
STEP 11How industry does it

ReAct (Reason+Act) is the foundational agent pattern — it's what LangChain agents, the OpenAI Agents SDK, and Cursor/Cody's chat all implement under the hood. Production concerns I handle by hand (tool-call caps, graceful degradation, streaming) are exactly what those frameworks provide; I hand-rolled them to own the mechanics + guardrails.

💬 Interview Q&A

How does the agent loop work, and when does it stop? Prompt (RAG + tools) → stream LLM → if tool_calls, execute + feed back + loop; when it returns no tool calls, that's the final answer. Hard cap of 5 rounds as a backstop.
Why are the tools read-only? A chat agent shouldn't mutate state on a fuzzy instruction. Reads are safe; writes go through explicit, reviewable flows — GitHub PR creation (you review the PR) and the isolated sandbox.
A model spammed a tool in a loop. What did you do? De-dup identical calls; cap to 2/round & 3/turn then force a prose answer; cap tool-result size; treat rate-limit/413 as terminal. A tool_use_failed retries once without tools.
WebSocket vs SSE — why WS here? Chat is bidirectional/interactive (send, stream, stop) → WebSocket. One-way progress (ingest/agents) → SSE.
How do you avoid hallucinated file paths? Force file:line citations from the retrieved context, preload the real file inventory, and detect leaked tool-call text.

⚠️ Common mistakes this module avoids

  • Offering tools on every turn (wastes tokens; chit-chat skips them).
  • No stop condition or no round cap (infinite loops).
  • No guardrails against runaway tool calls.
  • Using the request-scoped DB session inside a stream (it gets torn down).
  • Trusting/executing model output directly.

Module 4 — Multi-Agent Pipeline

A structured orchestration for complex questions: a planner decomposes the task, researchers answer each part grounded in code, a synthesizer combines them, and a critic fact-checks — with a Reflexion self-correction loop. Where chat is one agent, this is a coordinated team, streamed stage-by-stage.

Files in this module

├── service.py                    AgentOrchestrator — _plan / _research / _synthesize / _review / _refine
└── schemas.py                    AgentRunRequest/Response, AgentStep, AgentReview
STEP 1Why this module exists
  • Hard questions benefit from decomposition (sub-questions) + verification (a critic) — a single pass can be confidently wrong.
  • It's the "agentic AI" showpiece — planner/researcher/synthesizer/critic + Reflexion.
  • It reuses the same retrieval + LLM as chat, at a higher level of orchestration.
One-liner: "It's a planner→researchers→synthesizer→critic pipeline with a Reflexion loop — decompose, ground each part in code, then fact-check and self-correct."
STEP 2Where it fits

A layer above chat: each researcher calls SearchService (Module 2) and the LLM (Module 10). It's stateless — a run reads the index and returns a result; nothing persisted.

Workflow vs agent: chat is an agent (LLM picks the next step); this is a structured orchestration (fixed stages, each powered by an LLM). Both agentic — name the distinction.
STEP 3How it communicates

SSE — each stage is an event streamed to the Agents page. The streaming endpoint opens its own DB session inside the generator (the request-scoped one is torn down before the body runs):

STEP 4Data & state

No tables — a run is ephemeral. It reads the index (Qdrant + Postgres via search) and returns an AgentRunResponse (plan, steps, synthesis, review, refined flag).

STEP 6Pipeline flow
  1. Planner — task → a few focused sub-questions (JSON).
  2. Researchers — one per sub-question, each answers grounded in retrieved code (RAG).
  3. Synthesizer — combine findings into one coherent answer.
  4. Critic — fact-check the answer against the findings → verdict (accurate / issues / uncertain) + notes.
  5. Reflexion — if "issues", feed the critique back to revise once, then re-review.
task ─▶ Planner ─▶ Researcher×N (RAG) ─▶ Synthesizer ─▶ Critic ─┬─ accurate ─▶ done └─ issues ─▶ Reflexion(revise once) ─▶ re-review ─▶ done
STEP 7Edge cases
  • A stage's LLM call fails — guarded: it degrades to a partial result, not a 500.
  • No findings (all research empty, often a rate limit) — synthesizer says so plainly.
  • Critic uncertain — surfaced as its own verdict, no revision forced.
  • Reflexion — bounded to one iteration so it can't spin forever.
STEP 8Best practices
  • Guard every LLM call — a failure degrades gracefully.
  • Bounded Reflexion — revise once, re-review; never an open loop.
  • Reuse retrieval — researchers use the same tuned SearchService.
  • Own DB session in the streaming generator.
  • Stream stages — the user watches Plan → Research → Synthesize → Critic live.
STEP 9Security concerns
  • Same authz as search — only the caller's ready repos are researched.
  • No writes — the pipeline only reads + reasons; it can't mutate anything.
  • Token/cost exposure — a run is 5–8 LLM calls; the model defaults to 8B to stay in budget.
STEP 10Scalability
  • Sequential stages today (rate-limit friendly on the free tier); researchers could run in parallel to cut latency.
  • Token cost is the real limit — 5–8 calls per run; mitigated with the 8B default + guarded calls.
Gold: "How would you speed it up?" → parallelize the independent researchers (they don't depend on each other), at the cost of a burst against the LLM rate limit.
STEP 11How industry does it

Multi-agent orchestration is the frontier: AutoGen, CrewAI, and LangGraph all model planner→worker→critic crews; the Reflexion and self-critique / agent-as-a-judge patterns come straight from the research literature. My pipeline is a hand-rolled version of exactly these patterns, which is why I can explain every stage rather than defer to a framework.

💬 Interview Q&A

What's the difference between a workflow and an agent? A workflow has fixed, developer-defined control flow; an agent lets the LLM decide the next step. Chat is an agent; this pipeline is a structured orchestration (fixed stages, each LLM-powered).
Why add a critic? A single LLM pass can be confidently wrong. An independent critic fact-checks the answer against the researchers' grounded findings and catches unsupported claims.
What is Reflexion? Self-correction from feedback: on a "issues" verdict, feed the critique back to revise the answer once, then re-review. Bounded to one iteration so it can't loop forever.
How does this differ from the chat agent? Chat = one LLM-driven tool loop. This = multiple specialized stages orchestrated deterministically, each grounded in retrieval, with verification built in.
What happens if one stage's LLM call fails? Every call is guarded — it degrades to a partial result (e.g., a missing researcher finding) rather than crashing the whole run.

⚠️ Common mistakes this module avoids

  • Unbounded self-correction loops (Reflexion is capped at one).
  • Trusting a single confidently-wrong pass (the critic verifies).
  • Researchers answering ungrounded (each uses RAG).
  • Crashing the whole run when one stage fails (guarded degradation).
  • Using the request-scoped DB session in the SSE generator.

STEP 6Login flow
  1. Look up user by email.
  2. Verify password with Argon2 (deliberately slow).
  3. On failure: write an audit row, return a generic invalid_credentials (no enumeration).
  4. On success: issue a short-lived access JWT + an opaque refresh token (stored hashed); audit the login.
  5. Refresh: validate → revoke the used token (single-use) → issue a fresh pair (rotation).
STEP 7Edge cases
  • User enumeration — unknown user & wrong password return the identical error.
  • Refresh reuse — a revoked refresh token presented again signals theft → reject.
  • Expired access token — the frontend refreshes once on a 401 and retries.
STEP 8Best practices
  • Argon2id for passwords (memory-hard, brute-force resistant).
  • Deny-by-default permissions.
  • Short access TTL + revocable refresh.
  • Thin views / fat services; uniform error envelope.
  • Hash refresh tokens at rest; never log raw tokens.
STEP 9Security concerns

Argon2 · generic errors · hashed + rotated refresh tokens · short access TTL · RBAC guards · audit logging. Future: HS256 → RS256 with keys from a secret manager; MFA for destructive actions.

STEP 10Scalability
  • Stateless access tokens → the API tier scales horizontally with no shared session store.
  • Authorization is O(1) from token claims — no DB hit per request.
Gold: "Cost of permissions-in-token?" → staleness until the token expires; mitigation is a short TTL (+ a denylist for hard revocation).
STEP 11How industry does it

Enterprises rarely build the IdP — they front it with Okta / Auth0 / Azure AD / Cognito (OIDC/SAML), auto-provision via SCIM, and enforce MFA. My build models the same primitives (Argon2, JWT, rotation, RBAC) and would slot an external IdP in behind the same interface.

💬 Interview Q&A

JWT vs sessions? Stateless scale vs revocability — I use both: a short-lived self-validating access token + a revocable, rotated refresh token.
Why refresh-token rotation? Single-use: each refresh is revoked and replaced. A reused (already-revoked) token signals theft → reject / revoke the family.
Where do you check permissions, and why there? In dependency guards from token claims — centralized, no scattered ifs, no DB hit per request.
How do you stop enumeration / brute force? Identical generic errors for unknown-user vs wrong-password, plus (prod) rate limiting.

⚠️ Common mistakes this module avoids

  • Long-lived access tokens with no revocation (split access/refresh).
  • Storing raw refresh/reset tokens (hashed at rest).
  • Checking role == "admin" in code (check permissions/roles via guards).
  • Leaking which emails exist (generic errors).

STEP 8Best practices
  • Protocol + factory — depend on abstractions, not SDKs.
  • Normalize provider quirks in the adapter, not the caller.
  • Retry/backoff on transient errors; batch embeddings.
  • Config over code — one env var to switch.
STEP 9Security concerns

API keys live server-side in config only; base_url is configurable (for self-hosted inference); nothing provider-related is exposed to the frontend.

STEP 10Scalability

Swap to faster/cheaper providers as load changes; run local models to cut cost; the abstraction means that's a config change, not a rewrite.

STEP 11How industry does it

The same idea powers LiteLLM and OpenRouter (one interface for many models). The OpenAI-compatible API has become a de-facto standard — which is exactly why my one adapter serves OpenAI, Groq, vLLM, and LM Studio.

💬 Interview Q&A

How is the app model-agnostic? A Protocol (chat/stream/embed) + a factory that returns Ollama/OpenAI/Groq from config, even per conversation. The rest of the code depends on the Protocol, never a concrete SDK.
What broke when you switched embedding providers? Dimensions/semantics differ across models, so vectors aren't comparable — the collection dimension must match; I re-ingest. Also added 429 retry/backoff.
Why the abstraction instead of just calling OpenAI? Vendor independence (self-hostable), testability (fakes), and cost flexibility (local in dev, Groq in prod).

⚠️ Common mistakes this module avoids

  • Hardcoding one provider's SDK across the codebase.
  • Leaking provider quirks (streaming formats) into business logic.
  • Mixing vectors from different embedding models.
  • No retry/backoff against rate-limited providers.

Module 11 — Observability & Deployment

The production-readiness layer: Prometheus metrics, structured logging with request correlation, token/cost accounting, and three deployment modes (Docker Compose, Helm/K8s, free-tier split). You can't operate what you can't see.

Files in this module

core/metrics.py            Prometheus counters + histograms (aca_*)
core/logging.py            structlog, request_id/trace_id propagation, secret redaction
core/cost.py               tiktoken token counting + USD cost estimation
api/middleware/            request_id · metrics · rate_limit
docker-compose.yml · infra/helm/aca · render.yaml · apps/web/vercel.json
STEP 1Why this module exists
  • An LLM app without observability is a black box — you can't debug latency, cost, or failures.
  • Cost is a first-class concern with paid LLMs — it must be measured.
  • It's what makes the project production-shaped, not a demo.
One-liner: "Prometheus metrics + correlated structured logs + token/cost accounting, deployable three ways with graceful degradation."
STEP 2Where it fits

Cross-cutting — middleware wraps every request; metrics/logging/cost instrument every layer. Deployment configs sit at the repo root + infra/.

STEP 3How it communicates

Exposes /metrics (Prometheus scrape), emits JSON logs (shipped to any aggregator), and Grafana reads Prometheus. Celery uses multiprocess metrics aggregation.

STEP 4Signals

Metrics (aca_*: HTTP, LLM calls/tokens/latency, tools, search, ingest, cost), structured logs (with request_id), and derived cost. No DB tables.

STEP 5Endpoints

/metrics (Prometheus), /health (liveness), /api/v1/ready (readiness — Postgres/Redis checks).

STEP 6Request flow (instrumentation)
  1. request_id middleware — generate/propagate a correlation id, bind to structlog.
  2. metrics middleware — count + time the request by route/status.
  3. rate_limit middleware — Redis sliding window (fails open).
  4. Each LLM call records tokens → cost.py → a Prometheus cost counter.
STEP 7Edge cases
  • Celery multiprocess — aggregate metrics across worker children.
  • Redis down — rate limiter fails open (availability over a perfect limit).
  • Free-tier cold start (~30–60s) — measured + documented; a keep-warm pinger mitigates.
STEP 8Best practices
  • Request-id correlation — every log line in a request shares an id.
  • Consistent metric naming (aca_<area>_<thing>_<unit>).
  • Cost accounting surfaced in Grafana + the UI.
  • Health vs readiness split; secret redaction in logs.
STEP 9Security concerns

Rate limiting (Redis sliding window), production security headers (HSTS, etc.), and secret redaction in logs (passwords/tokens/keys never logged).

STEP 10Scalability & deployment
  • Three modes: Docker Compose (local, 9 services), Helm/K8s (HPA/PDB/NetworkPolicy/Ingress), free-tier split (Render/Vercel/Neon/Upstash/Qdrant/Groq/Jina).
  • Graceful degradation: inline ingestion when there's no worker; sandbox off without a Docker socket.
  • Stateless API + HPA scales horizontally.
STEP 11How industry does it

The standard is the four golden signals (latency, traffic, errors, saturation), OpenTelemetry tracing, and 12-factor config. My Prometheus/structlog/cost stack covers the essentials; the next step is OTel spans across search → LLM → tools for full request tracing.

💬 Interview Q&A

How do you observe the system? Prometheus metrics (aca_*), structured logs with a request_id per request, Grafana dashboards, and per-LLM-call cost accounting.
How do you track LLM cost? cost.py counts tokens with tiktoken × a per-1M-token price table (local = free) → a Prometheus counter + a token meter in the UI.
Why does the rate limiter "fail open"? If Redis is unreachable, allowing the request preserves availability — a rate limit is a non-critical control, so availability wins.
What are your deploy modes and their trade-offs? Docker Compose (local), Helm/K8s (production), free-tier split (portfolio) — the last trades cold starts + tight limits for zero cost, with graceful degradation.

⚠️ Common mistakes this module avoids

  • No request correlation (undebuggable logs).
  • Logging secrets/tokens.
  • No cost visibility on paid LLMs.
  • A rate limiter that fails closed (Redis outage = full outage).
